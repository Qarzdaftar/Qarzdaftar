# QARZ DAFTAR — lokal web ilova

TypeScript/Express 5 + PostgreSQL 18 (local tests) + Drizzle schema/migrations, node-postgres transactions, server-served HTML/CSS/vanilla JavaScript. **Not deployed**; merchant checkout and real SMS remain disabled by default. Store IDs scope API queries. Money is integer UZS. Do not enter real customer details in test environments.

## Setup

Node 22+ and PostgreSQL 16+ (production: managed/installed PostgreSQL, backed up and access-controlled). Docker is not required for tests: `npm run test:db` starts an isolated genuine PostgreSQL cluster using the dev-only `embedded-postgres` package, applies migrations, runs tests, and stops it with `pg_ctl`. It never substitutes an in-memory database in the server. On Windows the cluster is loopback-only; fixture password/port and data are ephemeral. Do not run this test script on production data.

1. `npm ci`
2. Set `DATABASE_URL` in environment (see `.env.example`; file is documentation, app does not auto-load it). Create the database yourself; least-privileged runtime account and separate migration account are recommended.
3. `npm run db:migrate`, `npm run build`, `npm start` (API defaults to port 4000).
4. `npm run dev` for local development. Open `http://127.0.0.1:4000/` (public landing) or `/app` (authenticated product). `GET /health` checks PostgreSQL.
5. `npm run test:db` runs real DB integration tests (no real SMS). `npm run build` typechecks server.

Release QA and remaining safety gates: [RELEASE_QA.md](RELEASE_QA.md). `npm run test:restore` exercises an isolated, synthetic PostgreSQL cold physical copy/restart (Windows embedded package); it never touches your configured `DATABASE_URL`. Optional local-only `docker compose up --build` provides a disposable DB, one-shot migrations and loopback app at port 4000; Docker execution has not been verified on this host. Do not reuse this Compose configuration/credentials/volume for production, and do not run a migration against a real customer DB without a separately approved backup/restore plan.

For production: HTTPS reverse proxy and `NODE_ENV=production`, HTTPS `PUBLIC_ORIGIN`, secret handling, backups, monitoring, migration rollout and privacy review are prerequisites. `TRUST_PROXY=1` only behind one trusted proxy. No account/customer phone verification endpoint is offered; do not present a customer self-view until a real verified-phone OTP flow is separately implemented.

## UI and SEO contract

`src/app.ts` serves `public/index.html` at `/`, `public/app.html` at `/app` and static files from `/assets`. Public landing is readable HTML with visible FAQs and truthful SoftwareApplication offers; no mock records enter the database (the decorative hero card says “NAMUNA”). Pricing: 14-day trial, 1 month 60 000 UZS, 2 months 100 000 UZS. Paid CTAs are disabled while merchant checkout is unavailable. Private app is always `noindex` and API sessions are cookie-based; `GET /api/auth/csrf` rotates and returns an in-memory CSRF token after page reload (old token becomes invalid). Customer self-view and browser platform-owner aggregate are intentionally gated, not simulated. The app reads real `/api` routes for signup/login/logout, customers/debts/payments, audit, reports, export, subscription and SMS settings/outbox. Employee menus hide admin-only functions; the backend enforces authorization independently. API response shape remains `{data}` / `{error}` (see below and SUBSCRIPTION.md).

No production domain is known. Without a valid HTTPS `PUBLIC_ORIGIN`, landing includes `noindex`, robots disallows all, and sitemap returns 404. With a configured HTTPS origin, `/` gets a canonical, `/robots.txt` allows the public page but disallows `/app` and `/api/`, and `/sitemap.xml` lists only `/`. Set the real verified domain and review public metadata/structured data before publishing. Static files are copied unchanged by `npm run build` because paths resolve from `dist/app.js` to project `public/`; a deployment must include `public/` alongside `dist/` and runtime dependencies. Google Fonts is optional; system font fallback works offline.

Browser QA (local fixture only): `npm run build` then `node scripts/browser-qa.mjs` starts temporary PostgreSQL and app at `http://127.0.0.1:4310`; `python scripts/chrome-qa.py` drives an isolated Chrome DevTools instance on port 9229 (see UI_REPORT.md). Stop the QA server after tests. Never use it with customer data. Browser-use integration was unavailable in this run, so independent local Chrome/CDP was used. Do not open the QA port publicly.

## REST contract

All responses: `{ "data": ... }` or `{ "error": { "code", "message", "issues"? } }`. Authentication is an argon2id password with a 7-day opaque hashed-session cookie (`httpOnly`, `SameSite=Strict`; `Secure` in production); state mutations after login require `X-CSRF-Token` returned by register/login. Keep this token in memory, not persistent browser storage. Email is normalized lowercase. `/api/auth/register` creates one store/admin and starts its only 14-day trial; `/api/auth/login`, `/api/auth/me`, `/api/auth/logout`; `/api/employees` (admin). Credentials: email, password (12–200 chars); register adds storeName.

- `POST /api/customers`: `{name, phone, consentEvidence}`. Evidence must document actual customer consent; `consentAt` is server time. Phone normalized to `998XXXXXXXXX`. Duplicate active phone per store => 409; `GET /api/customers?search=...`; `PATCH /api/customers/:id` `{archived?, optedOut?}`. Archive is reversible; opt-out stops SMS.
- `POST /api/debts`: `{customerId, items:[{title, quantity, unitPrice}], description?, dueDate?}`. Backend computes each `lineTotal` and integer `total`; supplied client total rejected. Dates ISO `YYYY-MM-DD` local due date. `GET /api/debts?customerId=...`, `GET /api/debts/:id` show derived balance and items. No dueDate => no scheduled reminder.
- `POST /api/payments`: `Idempotency-Key: <UUID>` and `{customerId, allocations:[{debtId,amount}]}`. Sum from allocations only; partial/full supported, excess returns 409, replay with same key/body returns 200, mismatched body 409. DB transaction locks store/debt rows; simultaneous double-pay rejected. `POST /api/payments/:id/reverse` `{reason}` admin-only, preserves record and audit. `GET /api/payments`.
- `GET /api/reports/summary?days=7|30|365`: totals and period totals scoped by store; `GET /api/audit` admin-only; `GET /api/export` admin-only JSON export of all customer/debt/payment/allocation records (sensitive, no-store). List endpoints currently cap at 100; export is unbounded and needs streaming for very large shops.
- `GET/PATCH /api/stores/settings`: admin-only mutation for smsEnabled, smsHour/smsMinute (Asia/Tashkent), dailyCap, smsCostCap, smsUnitCost and sender (1–11 ASCII letters/digits, or null). `GET /api/sms/outbox` admin-only; `POST /api/sms/outbox/:id/retry` admin-only, only explicitly rejected send.

Trial expiry (or expired paidUntil) blocks new debt creation and reminder sends with 402; existing debts/payments remain readable/exportable, existing repayments and reversals remain allowed. One trial is created per store at registration; login cannot restart it. Multiple stores using different emails remain possible and require abuse protection before launch. Subscription plans, admin status/warnings/history, optional Payme checkout and platform reporting are documented in [SUBSCRIPTION.md](SUBSCRIPTION.md). No live charges or merchant sandbox validation have occurred; checkout is disabled by default.

## SMS integration boundary

Official Play Mobile HTTP API: `https://send.smsxabar.uz/broker-api/send`; Basic auth, JSON UTF-8, `recipient` without `+`, unique `message-id` per attempt <=40 chars, `sms.originator` and `sms.content.text`. `200 Request is received` means accepted, not delivered. Provider posts `messages` statuses to partner `/status`; docs do not specify callback authentication, so this implementation requires an unpredictable 32+ character callback URL secret (`/api/provider/playmobile/:secret`) registered privately with provider; deploy behind TLS proxy that redacts paths from logs and allowlists provider IPs. Never register/open this URL publicly until security and sender approval. Status transitions to delivered/transmitted/etc only on validated callback. Callback cannot turn `unknown` automatically into delivered; manual reconciliation needed.

Worker `node dist/worker.js` exits disabled unless `SMS_LIVE_ENABLED=1`, `SMS_SENDER_APPROVED=1`, `PLAYMOBILE_APPROVED_SENDER` (exact contracted sender, 1–11 ASCII alphanumeric), both Play Mobile credentials, callback secret and DB URL are set. Setting flags could send REAL paid SMS; **do not enable without separately scoped permission**. Worker checks trial, due date, unpaid balance, consent/opt-out, schedule one-hour window Asia/Tashkent, daily cap and configured unit-cost cap on dispatch; approved sender must match store sender. Store row lock is held through the bounded provider call, serializing repayments/opt-out/settings with transmission. Daily outbox `(debt,date)` is unique; accepted/unknown aren't automatically retried; stale processing becomes unknown. Explicit 400 validation rejections may be manually retried with a new message-id. Single-segment GSM-7 content is deliberately fixed; carrier tariff, sender authorization and actual cost MUST be confirmed before live enablement. See REPORT.md for provider research, tests, and gaps.
