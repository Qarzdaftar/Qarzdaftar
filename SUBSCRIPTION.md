# QARZ DAFTAR — obuna va to‘lov chegarasi

Bu kod lokal backend integratsiyasi, **ishlab turgan merchant to‘lovi emas**. Hech qanday real charge yoki Payme sandbox callback sinovi o‘tkazilmadi. Default `.env.example` bilan checkout va Payme callback 503/401 holatida o‘chirilgan. Productionga chiqarish uchun merchant shartnomasi, rasmiy sandbox sertifikatsiyasi, komissiya/soliq/refund qoidalari, HTTPS reverse proxy va egasining alohida ruxsati talab qilinadi. Frontenddagi “paid” yoki return URL hech qachon access bermaydi.

## Tarif va kalendar qoida

`src/subscription.ts` → `PLANS`: 1 oy — **60 000 UZS**, 2 ketma-ket oy — **100 000 UZS** (ikkita bir oylikka nisbatan 20 000 UZS tejash). Narx integer UZS, Payme protokolida `×100` tiyin. Migratsiyada shu narxlarni himoyalovchi constraint bor; narx o‘zgarsa ikkalasini birga yangi migratsiya bilan yangilang. 14 **mahalliy kalendar kuni** trial do‘kon yaratilganda DB `now()`dan Asia/Tashkent devor-soatiga +14 kun. Bir store uchun bitta trial; login/checkout uni qaytadan boshlamaydi. Turli email bilan boshqa store ochishni oldini olish uchun identifikatsiya/anti-abuse hali kerak.

Timestamps PostgreSQL `timestamptz`da saqlanadi va API ISO UTC qaytaradi; foydalanuvchiga Asia/Tashkent ko‘rsatiladi. Obuna xaridi `max(server now, trialEndsAt, paidUntil)` dan boshlanadi; oldindan yangilash access vaqtini yo‘qotmaydi. Shu mahalliy sana+vaqtga PostgreSQL `make_interval(months => N)` qo‘shiladi, so‘ng `AT TIME ZONE 'Asia/Tashkent'` orqali UTC instantga aylantiriladi. Oyda bunday kun bo‘lmasa clamp: Jan 31 +1 oy → Feb 28 (kabisa yili Feb 29), +2 oy → Mar 31. Keyingi mustaqil xarid *joriy tugash sanasidan* boshlanadi: Feb 28 +2 oy → Apr 28; original Jan 31 anchorini tiklamaydi. Tashkent amaldagi qoidada DST yo‘q; vaqt zonasi siyosati o‘zgarsa PostgreSQL tzdata mahalliy vaqtni yechadi, release oldidan yangi DST o‘tishlarini test qiling. Expiry instant eksklyuziv (`end > now()`), server soati ishlatiladi. Trial T−3/T−1 ogohlantirishlari DBdagi Asia/Tashkent **sana** farqi bo‘yicha, faqat `trial` state uchun.

`trial` → `active` (tasdiqlangan Perform), `expired` (instant o‘tdi), `cancelled` (admin bekor qilishni belgiladi, muddati tugaguncha access saqlanadi; auto-renew umuman yo‘q). Yangi muvaffaqiyatli xarid cancellation flagini tozalaydi. `POST /api/subscription/cancel` pulni qaytarmaydi, provider transaksiya cancel emas. Muddati tugagach yangi qarz va SMS enqueue/dispatch to‘siladi (server-side, dispatch send oldidan qayta tekshiradi); avvalgi qarz/to‘lov/o‘qish/eksport qoladi. Mijozni “garov” qilmaslik uchun qarz qaytarimini yozish va admin reversal **ruxsat**. Customer yaratish ham mumkin, qarz emas. SMS pullik provider xizmati **obunaga kiritilmagan**: `smsBillingPolicy = separate_unpriced`; do‘konning SMS caps/unit cost sozlamasi haqiqiy tarif emas. Contract/tarif va egalik tasdiqlanmaguncha hech qachon “SMS included” deb aytmang.

## API (standart `{data}` / `{error}`)

- `GET /api/subscription/plans` — ommaviy narxlar, `trialDays`, `checkoutAvailable`, `smsBillingPolicy`.
- `GET /api/subscription` — login talab: storeId, state, trialStartedAt, trialEndsAt, paidUntil, accessUntil, planMonths, serverNow, daysRemaining, `warning: TRIAL_T_MINUS_3|TRIAL_T_MINUS_1|null`.
- `GET /api/subscription/history` — faqat store admin; attempts+events store ID bo‘yicha. Audit `subscription.activated`/`subscription.cancelled` ham mavjud.
- `POST /api/subscription/initiate` — admin cookie + `X-CSRF-Token` + `Idempotency-Key: UUID`, body `{ "months": 1 }` yoki `{ "months": 2 }`; response `attemptId,status,provider,amountUzs,planMonths,checkoutUrl` faqat merchant yoqilgan bo‘lsa. Bir xil store/key/plan qayta yuborilganda aynan shu attempt; boshqa plan bilan 409. Frontend summani yoki return URLni “paid” deb bildira olmaydi.
- `POST /api/subscription/cancel` — admin + CSRF, faqat access muddatigacha; access end o‘zgarmaydi.
- `GET /api/platform/subscriptions/summary` — **faqat server-to-server** `Authorization: Bearer <PLATFORM_REPORT_TOKEN>` (32+ belgili), do‘kon admin cookie bu huquqni bermaydi. totalStores/trial/active/expired/cancelled, current Tashkent month gross paid revenue, byPlan, failedPayments (`cancelled` + `failed` attempts), 3 kunlik upcomingExpiries. DB-derived global aggregate, mijoz PII qaytmaydi. Platform browser dashboard uchun alohida identity/session va permission tizimi hali yo‘q; bearer secretni brauzerga yuborish TAQIQLANADI.

`GET /api/auth/me` store fieldlarida trial/paid dates bor, lekin UI ogohlantirish uchun `/api/subscription` authoritative. Private routes HTTPS/no-store cache reverse proxy bilan himoyalansin; public UI keyinroq qo‘shiladi.

## Payme adapteri va operator checklist

Rasmiy [Merchant API](https://developer.help.paycom.uz/metody-merchant-api/), [request Basic auth](https://developer.help.paycom.uz/protokol-merchant-api/format-zaprosa/), [checkout GET tiyinlari](https://developer.help.paycom.uz/initsializatsiya-platezhey/otpravka-cheka-po-metodu-get/), [sandbox](https://developer.help.paycom.uz/pesochnitsa), [CreateTransaction](https://developer.help.paycom.uz/metody-merchant-api/createtransaction/), [PerformTransaction](https://developer.help.paycom.uz/metody-merchant-api/performtransaction/) va [CancelTransaction](https://developer.help.paycom.uz/metody-merchant-api/canceltransaction/) asosida bitta `/api/provider/payme` JSON-RPC adapteri: Basic `Paycom:<merchant key>` doimiy vaqt bilan qiyoslanadi; amount (tiyin)/account.order_id/provider transaction ID DBdagi attemptga tekshiriladi; `CheckPerformTransaction`, `CreateTransaction`, `PerformTransaction`, `CancelTransaction`, `CheckTransaction`, `GetStatement` amalga oshirilgan. `PerformTransaction`gina do‘kon locki ostida atomik `paidUntil`, attempt va event/auditni o‘zgartiradi. Duplicate Create/Perform/Cancel javobi idempotent; provider ID unique, bir attemptga boshqa ID rad. Yo‘q/noto‘g‘ri Basic auth yoqilgan adapterda 200 JSON-RPC `-32504`, o‘chirilgan adapterda 503; boshqa RPC xatolari 200 JSON-RPC error. `CancelTransaction` faqat to‘lanmagan reservationni cancel qiladi; xizmat darhol berilgani uchun to‘langan transactionga `-31007` qaytaradi. Refund/dispute va Payme sertifikatsiya siyosatini merchant bilan alohida hal qilmasdan productionga yoqmang. `GetStatement` 31 kunlik oynaga, 1000 yozuvga cheklangan — yirik volume bo‘lsa sertifikatsiyadan oldin pagination/statement reconciliation dizayni kerak.

[Solishtirish] Payme checkout + Basic-auth JSON-RPC callback: merchant web-kassa ID va TEST_KEY kerak, sandboxdagi Create/Perform/Cancel tekshiruvi talab qilinadi. [Click SHOP API](https://docs.click.uz/shop-api/) Prepare/Complete ikki bosqichli callback talab qiladi; bu kodda Click implementatsiyasi yo‘q. [OSON Kassa](https://docs.oson.com/) invoice create/status/refund va [sha256 signatureli HTTPS notification](https://docs.oson.com/kassa-oson/notification) beradi; secret token merchant onboardingdan keyin beriladi. Bu alternativalardan birining mavjudligini Payme kaliti bilan adashtirmang. Rasmiy sahifalarda do‘konning aynan shu shartnomasi uchun fee/komissiya/SMS tarifi tasdiqlanmadi: owner merchant bilan yozma kelishuv va narx/tax/chargeback siyosatini olish kerak. Soxta “sandbox passed” da’vosi yo‘q.

1. Yuridik shaxs/merchant ro‘yxatdan o‘tadi; web kassada `account.order_id` nomini va `https://<real-host>/api/provider/payme` endpointini moslaydi. Secretlarni vault/process managerda saqlaydi, `.env`ni gitga qo‘shmaydi; webhook HTTPS va rate-limit/WAF, maxsus logging redaction, key rotation, monitoring. `PUBLIC_ORIGIN` va `TRUST_PROXY=1` faqat ishonchli reverse proxyda.
2. Izolyatsiyalangan sandboxda `PAYME_CALLBACK_ENABLED=1`, `PAYME_CHECKOUT_MODE=sandbox`, `PAYME_MERCHANT_ID`, `PAYME_KEY=<TEST_KEY>` (faqat test muhiti) bilan integration/cancel/retry/refund/amount mismatch/reconciliation sinaydi. Mahalliy `tests/subscription.test.ts` *sintetik mock callback*, Payme xizmatining o‘ziga ulanmaydi.
3. Real production charge uchun egadan aniq ruxsat, merchant production key, huquqiy/security review va provider sandbox sign-off OLGANDAN SO‘NG `NODE_ENV=production`, `PAYME_CHECKOUT_MODE=production`, `PAYME_CALLBACK_ENABLED=1`, `PAYME_PRODUCTION_APPROVED=1` va haqiqiy merchant config. Boshqa kombinatsiyalar checkout/callbackni o‘chiradi. Faqat frontend bayrog‘ini o‘zgartirish to‘lovni faollashtirmaydi. Hech qanday live key yoki charge bu vazifada ishlatilmadi.

`npm run build && npm run test:db` haqiqiy lokal PostgreSQL clusterda migrations + sintetik callbacks. `drizzle/0002_subscription.sql` mavjud installlar uchun backfill/constraint qo‘shadi; `0003_chemical_mandrill.sql` no-op snapshot-sync (generate tool diffini 0002 allaqachon bajaradi). Migratsiyalarni backup va stagingdan keyin productionga qo‘llang.
