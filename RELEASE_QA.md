| Backups/security | Real managed Postgres, encrypted offsite logical backups, actual restore of a production-format backup, retention/privacy policy, least-privilege DB roles, CSP/security headers at TLS edge, distributed rate limiting and trusted proxy rules need review. Current process-local limiter is unsuitable for replicas. |

Render official docs: [free web service](https://render.com/docs/free) spins down after 15 minutes idle; Free PostgreSQL expires in 30 days, supports **no backups**, and is unsuitable for persistent customer debt data. [Paid database backups](https://render.com/docs/postgresql-backups) include PITR, subject to plan/retention. No spending authorization or known price for this project. [Vercel Express docs](https://vercel.com/docs/frameworks/backend/express) say `express.static` will not serve static assets there as-is, and [Vercel Postgres docs](https://vercel.com/docs/postgres) require an external provider; this app's long-running SMS worker and DB migrations also require separate services. Do not deploy the current monolith to Vercel unadapted. A persistent Render or other approved Node service with managed Postgres, separate migration job and scheduled/worker service is a candidate **only after owner-scoped approval and budget**. Do not touch TEZGUL services.

## Deployment and monitoring runbook (not executed)

1. Owner specifies authenticated target account/service, project/repo, verified HTTPS domain, DB region/data residency, data classification/retention, expected cost and cap, provider onboarding and explicit approval for publication, migrations, live charges and outbound SMS separately. Secure repository audit happens in downstream GitHub task. No real customer data in disposable fixtures.
2. Build immutable image with source, `public/`, migrations and tested runtime Node 22; run container smoke and migration in staging against a **new** managed PostgreSQL. Back up staging DB and verify restoration into another empty DB before migration; review migration lock/downtime and obtain separate consent before any production migration. Do not run `npm run test:db` against production.
3. Configure secret `DATABASE_URL` and backend-only provider keys in platform secret store, not git. `NODE_ENV=production`, HTTPS `PUBLIC_ORIGIN` only after domain verification; `TRUST_PROXY=1` only when behind exactly one trusted proxy. TLS, HSTS, HTTPS redirects, private API cache-control and origin isolation must be checked end-to-end; paid/SMS env flags stay 0 until their independent gates pass.
4. Configure Postgres automated encrypted backups and offsite retention, access-controlled restore exercises; with standard PostgreSQL clients an operator can create a custom-format `pg_dump -Fc -f <restricted-path> <DB_URL>` and restore into an **empty, isolated** DB via `pg_restore --exit-on-error -d <new-DB-URL> <file>`, then verify counts, integrity and owner consent. Never expose dump URLs, secrets or customer PII; the local physical-copy drill above is not a substitute for this.
5. Health/readiness: `/health` returns 200 only if DB responds; monitor failed health, HTTP 5xx/429, signup and ledger error spikes, DB connection pressure/storage, pending/rejected/unknown SMS, trial warnings, payment webhook failure/duplicates, backup age and restore success. Redact auth cookies, phone, provider callback path and export payloads from logs. Test a staging restart and rollback using verified backups and immutable artifact.
6. Before any public launch: run live HTTPS/security headers/canonical/robots/sitemap and mobile/accessibility/performance checks, exercise real provider sandbox with approved keys, reconcile actual paid record and provider statement, document refund policy, verify consent and test only owner-authorized controlled SMS. No fabricated production URL or delivered-message claim.
